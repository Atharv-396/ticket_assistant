# Support Ticket Decision Assistant v2

An AI-powered, policy-grounded, multi-turn customer support decision system.

---

## What it does

A customer submits a support ticket. The AI:
1. Retrieves relevant company policy chunks (RAG).
2. Analyses the ticket against the policy.
3. If information is missing → asks a targeted question (IN_PROGRESS).
4. The customer replies and optionally uploads photos/evidence.
5. The AI re-retrieves policy + re-analyses the full conversation.
6. When enough information exists → produces a final policy-based recommendation (FINAL).

The complete conversation, all decisions, and evidence metadata are persisted.

---

## Architecture

```
Streamlit (browser)
      │  HTTP/REST only
      ▼
FastAPI backend
      ├── JWT auth (python-jose + bcrypt)
      ├── SQLAlchemy / SQLite
      │     ├── users
      │     ├── tickets   (status: open / closed)
      │     ├── messages  (role: user / assistant)
      │     ├── decisions (status: IN_PROGRESS / FINAL)
      │     └── evidence  (file metadata)
      └── Decision pipeline
            ├── RAG retrieval (Gemini embeddings + NumPy cosine similarity)
            ├── Gemini LLM (structured JSON decision with full conversation context)
            └── Pydantic validation (before any DB write)
```

## Setup

### 1. Prerequisites
- Python 3.11+
- Gemini API key from https://aistudio.google.com/app/apikey

### 2. Virtual environment
```bash
python -m venv .venv
.venv\Scripts\activate       # Windows
source .venv/bin/activate    # macOS/Linux
```

### 3. Install dependencies
```bash
pip install -r requirements.txt
```

### 4. Environment variables
```bash
copy .env.example .env
# Edit .env — add GEMINI_API_KEY and a random JWT_SECRET
```

Generate a JWT secret:
```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

## Multi-Turn Flow

```
User: "My product is damaged."
AI  : "Please provide the order value and photos of the damage."  [IN_PROGRESS]

User: "Order value ₹3,500, delivered yesterday."
User: [uploads photo.jpg]
AI  : "APPROVE_REFUND — damage confirmed above the ₹2,000 threshold."  [FINAL]
```

---

## Decision Actions

| Action | When used |
|---|---|
| REQUEST_MORE_INFORMATION | Critical details missing |
| REQUEST_PHOTOS | High-value damage claim (policy threshold) |
| APPROVE_REFUND | Damage/defect confirmed |
| REJECT_REFUND | Outside eligibility window |
| APPROVE_RETURN | Unopened non-food within 14 days |
| REJECT_FOOD_RETURN | Food product — not eligible |
| REPLACE_CORRECT_ITEM | Wrong item, within 7 days |
| OPEN_SHIPPING_INVESTIGATION | 8–10 days post-dispatch |
| OFFER_REPLACEMENT_OR_REFUND | >10 days, presumed lost |
| CANCEL_AND_REFUND | Pre-dispatch cancellation |
| NEEDS_MORE_INFORMATION | Too vague to apply any policy |
| *(+ more)* | See `schemas.py` VALID_ACTIONS |

## Security

- Passwords: bcrypt (never stored plain)
- JWT: HS256, secret from env, 60-minute expiry
- Ownership: all ticket queries filter by JWT user_id
- 404 returned for other users' tickets (no IDOR leakage)
- File uploads: content-type checked, 10 MB limit, UUID filenames
- No API key in source code


## Design Decisions

| Decision | Reason |
|---|---|
| Multi-turn via messages table | Full conversation preserved; Gemini sees all history |
| RAG re-runs on every turn | New info changes which policy chunks are relevant |
| IN_PROGRESS / FINAL status | Frontend clearly distinguishes questions from decisions |
| 404 for other users' tickets | Avoids leaking ticket existence (IDOR protection) |
| JSON text for list columns | SQLite has no array type; transparent and inspectable |
| NumPy cosine similarity | No vector DB needed for 7 chunks; fully explainable |
| Pydantic validates all LLM output | Never store unvalidated Gemini responses |
